# Observation signals

Adapted from Eoghan Henn / rebelytics.com, CC BY 4.0, pinned source `510caad26c907793e48306262af216ff9f71c9f7`.

Log when real work reveals a reusable methodology signal:
- the owner corrects a repeated or generalizable behavior;
- a documented skill rule is repeatedly violated;
- a repeated manual workflow could become a skill;
- a new tool makes an old step obsolete;
- a better test, review or safety method emerges;
- several skills need the same cross-cutting rule;
- a missing capability causes repeated founder work.

Do not log:
- one-off task facts;
- generic tool outages;
- preferences already encoded elsewhere;
- speculative improvements with no observed friction;
- observations that require exposing secrets/private client information.

Generalizability test: would the lesson still make sense in another task or another project using the same skill? Does it identify a missing rule, workflow or principle likely to recur? If mostly no, keep it in task context instead.

Before creating a new skill name, search current project skills and existing `proposes_skill` values. Dedupe first.
