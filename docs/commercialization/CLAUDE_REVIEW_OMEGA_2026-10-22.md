## Financial and security invariants to attack

1. No source mutation can turn an unpriced Apify event, a sandbox callback, locally authored SHA, pending charge or refund into cleared cash.
2. `verifyClearedPayment` is a dependency-injected function that must be bound to a trusted provider in an authenticated, sealed runtime to ever be considered evidence. Untrusted caller callbacks could be forged; no production path should accept a user-supplied function. Consider constraining the API to a non-user-injectable trusted adapter before future production release.
3. A legitimate routing/tracking phone link is NOT a proven revenue loss, and an unobservable site produces no billable finding.
4. Cross-run atomic charge reservation must use true shared PostgreSQL and the real platform's priced `verified-finding` event plus verified spending limit; a local process map is insufficient.
5. The Dockerfile includes the minimum import-graph files by generated allowlist; verify platform context handling and cold start in real Apify image, since Docker overlay storage prevented build here.
6. The browser can execute untrusted JavaScript under a sandbox, but route interception plus socket pinning should keep it read-only; test DNS rebinding, exotic navigation, service workers, iframes and malicious JS after obtaining a viable Chromium runtime.
