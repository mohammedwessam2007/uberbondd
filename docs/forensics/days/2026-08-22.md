* Give the agent mesh an entry point, and the two functions it needs to run

agent-mesh-control-plane composes the autonomy pump and the model workers
into a bounded cycle. It is the top of the cognitive bus, twenty-six modules
sit underneath it, and outside tests/ nothing imported it. No scheduler job,
no worker handler, no npm script, no workflow.

It was worse than unscheduled. runAgentMeshCycle requires an adapterFactory
and a compileRelayTask, and neither existed outside a test file: the only
adapterFactory in the repository was the stub `() => ({})` in a unit test,
and compileRelayTaskFromIntent was written, tested, and never passed to
anything. The first time an entry point existed, the cycle returned BLOCKED
with ["adapter-factory-required", "relay-task-compiler-required"].

chatgpt-relay-client -- the only implementation of the transport shape the
pump wants -- had no non-test importers either. Three complete, tested,
unreachable modules. A green suite does not distinguish "works" from "cannot
be reached", and 1535 passing tests said nothing about this.

Adds:

- scripts/agent-mesh-tick.mjs, one finite invocation. Bounded, non-resident,
  cloud-neutral, disabled unless AGENT_MESH_ENABLED is exactly "true".
  Distinct exit codes so a scheduler can tell DEGRADED from BLOCKED from a
  crash from the normal disabled resting state.
- src/agent-relay-adapter-factory.mjs, the adapterFactory the control plane
  actually means: a memoized chatgpt-relay-client per origin/target pair.
- src/agent-model-executor-factory.mjs, each worker's modelExecutor from its
  declared provider.

The two factories are named apart on purpose. I conflated them first time
through -- "adapterFactory" reads like the thing that talks to a model, and
it is not; it is the wire the compiled task travels over. The control plane
takes both.

A worker config arriving as JSON cannot carry a function, which is why the
tick script has to resolve both and attach them. Until now there was no way
to configure a worker from outside the process at all.

Refusals kept deliberate: a provider without both a pricing source and a
verification date is refused, because cost computed from unsourced pricing is
a number the system invented and the compute ledger would be quietly
fictional. A worker whose provider cannot be configured fails the tick by

indistinguishable from having no work.

* Enforce the activation gate, reach the sandbox provider, name the canonical spend path

Three more modules that were complete, tested, and unreachable.

The activation gate was the important one. agent-mesh-activation-gate decides
whether the mesh may call a model provider at all, and nothing ever built the
evidence input it takes -- so it had no callers, and the entry point added in
the previous commit would have called a provider with nothing between it and
the money.

It is now evaluated on every tick and enforced. Its four permitted modes map
onto worker execution, because a worker tick is the only thing in a cycle that
can call a provider: NO_PROVIDER_CALLS and SYNTHETIC_ONLY run none,
ONE_PROVIDER_CANARY runs one on a canary-ready provider,
BOUNDED_CLOUD_REHEARSAL runs all. Autonomy pumping is unaffected -- it relays
LOCAL_PREPARATION tasks and calls nothing.

agent-mesh-activation-evidence builds the gate's input from two sources kept
deliberately apart. First-hand facts the process checks itself -- is a
credential present, is pricing evidence present -- are always computed and can
never be overridden. Attested claims it cannot verify come from an operator
JSON file. A file cannot upgrade a first-hand fact, or the evidence file
becomes a way to talk the gate into opening; there is a test for that exact
attack. With no file at all the verdict is ARCHITECTURE_ONLY /
NO_PROVIDER_CALLS, which is the intended resting state. A file that is named
but missing or malformed is a refusal, not a fallback: a broken attestation
must not produce the same outcome as never having written one.

Withheld workers exit 3 rather than 0. A scheduler running happily forever
while the workers it was configured to drive never run once is the same silent
failure this entry point exists to remove.

claude-code-sandbox-executor is now the third provider. It drives a local
Claude Code CLI in an isolated sandbox and needs no pricing evidence, because
the CLI reports its own usage and total cost -- the number comes from the tool
that spent it. When the CLI reports no cost the executor returns UNCERTAIN
rather than zero, so unknown spend never looks free. It is a local process, not
free compute; it consumes whatever account it is configured against. It
requires an OS isolation receipt attesting an ephemeral filesystem, no mounted
business credentials, no reachable production network, and Anthropic-only

configured one. The gate scores only the two API providers, so a sandbox worker
has no canary readiness to look up and is never eligible under
ONE_PROVIDER_CANARY -- unknown reads as not-permitted, asserted by a test.

Make relay dispatch idempotent, so a crash mid-dispatch cannot pay twice (#89)

Making the mesh reachable made a real bug reachable too, and finding it was
only possible because the path now exists.

agent-autonomy-pump dispatches a task to the relay, and only afterwards does
agent-autonomy-job persist the run carrying the relayRef. Everything between
those two lines is a window in which the relay task exists and the run does not
know it -- a crash, an OOM, a container reclaim, or a failed snapshot write all
land in it.

createGithubRelayTask created a GitHub issue unconditionally. So the next tick
re-dispatched the same deterministic taskId and a SECOND issue appeared for one
task. Two workers claim two issues, do the work twice, and with provider-backed
workers that is two charges.

Reproduced directly before fixing: same input twice, two issues, one taskId.

The transport is now idempotent on taskId against open, not-done relay issues.
Four cases, each with its own answer:

- retry after a crash returns ALREADY_QUEUED and the existing issue number, so
  the run rebinds instead of re-dispatching. A distinct status, not a silent
  QUEUED: nothing was created, and a receipt saying otherwise is a lie an audit
  trail carries forever.
- the same id with different content is refused. Returning either version would
  be a guess about which caller is right.
- a task that already completed and closed may be dispatched again.
  Deduplication must not become a permanent ban on re-running an objective.
- a client that cannot list issues is refused outright, because it cannot tell a
  first dispatch from a retry, and creating on that assumption is exactly the
  unknown consequential state that must not proceed.

Identity comparison deliberately excludes createdAt, status and deadline. A
retry is by definition a second compilation at a later instant, so comparing
whole tasks would report every legitimate recovery as a conflict.

One further refusal, for the case that is neither "duplicate" nor "no
duplicate": if the first page of open relay tasks comes back full, an unscanned
page may hold the duplicate, and that is "cannot tell", not "none found". Fifty
concurrent open relay tasks is far past any expected load so it should never
fire, but reporting "cannot tell" as "none found" is precisely how a duplicate
charge slips through.

The regression test drops the post-dispatch run on the floor exactly as a killed
process would and asserts one issue exists after two ticks. Verified it fails
against the previous code by reverting the fix and re-running.

process dies in between, the fail-closed half already worked: that occurrence
can never be re-delivered, so no consequence happens twice.
