## Precise five-hour usage requirement

Let:

- B = five-hour baseline points for one *identical accepted task*, here 100.
- F = **truly unavoidable** initial interpretation/reasoning/substrate meter points, not free cash.
- R = fraction of **meter-weighted delegable original work** covered by *currently applicable, separately quality-accepted exact replay*. Not a count of tasks, source-byte savings or cached-input token volume.
- M = measured multiplier of the remaining unresolved work under a different chosen Claude plan model/route relative to the matching baseline. E.g., M = 0.5 means genuine **half the actual Pro usage** on identical quality work, not half an API tariff. Unknown until actual meter is read.
- H = total extra 5h-point cost of planning, scouting, agents, repeated prefixes, retries, verification interactions, compaction, etc.

**Usage model**: `U = F + (100-F)*(1-R)*M + H`.

**Minimum reuse share needed to target 5%**: `R >= 1 - (5-F-H)/[(100-F)*M]`, with **impossibility** when F+H >5. The optimizer refuses to call this a measured provider value.

Examples, each only mathematical:
1. F=0,H=0,M=1 => R must be **95%**, not 95% of ideas or files.
2. F=2,H=0.5,M=0.5 => R must be **94.8979592%** of delegable weighted work; R=.95 gives modeled U=4.95%.
3. F=6,H=0.5, even 100% replay leaves 6.5% usage => a 5% goal is impossible under those assumed costs.
4. F=0,H=0,M=.1 => even a 10x *genuine Pro-meter* improvement still needs R>=50%.
5. F=0,H=0,M=1,R=0 => U=100%; new difficult frontier problems cannot be declared cheap.
