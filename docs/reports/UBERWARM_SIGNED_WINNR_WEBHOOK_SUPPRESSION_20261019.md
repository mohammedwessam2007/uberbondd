# Winnr signed adverse-event suppression listener

**Purpose:** make the existing paid Winnr webhook service usable for genuine, no-extra-SaaS bounce/complaint protection, without any new sending authority.

- Source: `api/webhooks/winnr.mjs`, `src/uberwarm-winnr-webhook-suppression.mjs`, `migrations/20261019_winnr_webhook_suppression.sql`.
- Accepts only raw body verified using actual `X-Winnr-Timestamp` and `X-Winnr-Signature` HMAC-SHA256 with a trusted `whsec_` provider secret; 5-minute replay bound. Rejects unsigned, stale, malformed, oversized, missing-secret and missing-database input before any operational effect. All response bodies exclude raw provider payload and credentials.
- Event ID is transactionally deduplicated in protected Postgres; different payload under the same ID is rejected. Real authenticated `email.bounced` and `email.complained` events append the recipient to canonical `suppressions` in the same DB transaction, and ACK only after it commits and suppression readback succeeds. Existing suppression records are never removed or overwritten. Provider retries are idempotent. Positive events cannot clear holds or grant sending; `email.received` is recorded only as `REPLY_REQUIRES_REVIEW` and is not falsely counted as an accepted sales reply.
- The intended Vercel private app environment must already have **the canonical** `DATABASE_URL` and will additionally require a provider-generated, privately stored `WINNR_WEBHOOK_SECRET`; do not move secrets to repo, logs, comments or chat. Apply the additive migration to the exact database (not an unrelated live/restore DB); verify that both event table and canonical `suppressions` exist. Register an authenticated HTTPS Winnr webhook endpoint for the specific events only after source deployment, live route confirmation and secret custody verification. Do not activate public endpoint against a fake/empty shadow suppression table or store.
- A source merge or a 503 unconfigured route is NOT proof of live signed event ingestion, and a source unit test is NOT a provider webhook delivery receipt. Provider event log count must become independently nonzero for meaningful live coverage; an endpoint created with no events is not evidence of healthy mailbox reputation. This safety listener is no substitute for recipient-specific legal eligibility, opt-out page availability, sender health, exact campaign dispatch authority or cleared payments.
- Automated hostile tests include exact HMAC, signature rejection, timestamp expiry, event ID collision, no DB acknowledgement on suppression failure, and an **actual isolated PostgreSQL** migration+transaction+replay test. All production send paths remain unchanged and held.

Provider spec: https://winnr.app/help/api-mcp/webhooks.html . Regulator: https://www.ftc.gov/business-guidance/resources/can-spam-act-compliance-guide-business .

## Unsubscribe endpoint in the same existing Vercel application

`src/uberwarm-unsubscribe.mjs` provides an exact, permanent signed recipient token, scoped to `ALL_COMMERCIAL` mail. The protected sending system must build one per *actually authorized recipient* using a distinct `UBERWARM_UNSUBSCRIBE_SECRET`, and include the URL and a truthful sender postal footer in every commercial message. `api/unsubscribe.mjs` implements a safe `GET` confirmation page (no mutation, resists security-prefetch accidental opt-out) and an immediate one-click/form `POST` into canonical `suppressions` with positive readback before 200; failure returns 503 instead of a fake acknowledgement. The HMAC token itself must never be logged or copied into public receipts because it is a bearer suppression capability. The GET page does not display recipient data, and the response disables referrer leakage and caching. Unsubscribe tokens have no built-in expiration while the protected signing secret remains active, avoiding a 30-day expired opt-out failure. A secret rotation requires preserving old-key verification for outstanding campaign messages or suspending affected campaigns.

Live activation requires the existing canonical Vercel database, the private `UBERWARM_UNSUBSCRIBE_SECRET`, an externally tested browser POST and direct canonical suppression readback, plus protected campaign wiring. Neither deploying the API nor passing its fixture tests authorizes outreach. The separately scoped `WINNR_WEBHOOK_SECRET` and `UBERWARM_UNSUBSCRIBE_SECRET` are **not interchangeable**. An email body must also include a monitored reply STOP mechanism and sender postal identity, and a send must be blocked if any suppression query fails.

## Plain Vercel Node runtime adapter

Existing private Vercel project uses standard `api/*.mjs` Node functions with default-export `(req,res)` handlers. The added `src/uberwarm-vercel-node-bridge.mjs` exports that native entry point for both new routes while retaining pure `Request`/`Response` handlers for deterministic tests. It streams the **exact raw provider bytes**, without parsing/re-serializing the signed body; HMAC signature remains bound to original bytes. `api/webhooks/winnr.mjs` also exports `config.api.bodyParser=false` to avoid any framework JSON-parser swallowing the signed stream. Source tests send an actual Readable stream and confirm an extra whitespace byte rejects HMAC. A public 500 from a previous Vercel deployment is not an acceptable verified live endpoint, even when newer preview builds and hosted tests pass. Live route acceptance must be separately observed after a production deployment, with no blanket loosening of deployment protection or runtime secrets.
