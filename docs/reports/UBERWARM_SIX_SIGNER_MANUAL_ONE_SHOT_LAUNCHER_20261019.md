## Actual new operational composition

The earlier source delivered the exact approval-checked one-shot executor, but there was no runnable one-shot command or image. The production Railway image and 5-minute cron were deliberately read-only. We implemented a separate, manual `operator-tools/uberwarm2-execute-approved-once.mjs` and `Dockerfile.uberwarm-one-shot`; the monitored cron image and its start command stay unchanged. This script is deliberately **not called** by the existing production cron, any normal source import or build.

The launcher accepts precisely `--execute=<approved-probe-id>` plus an exact protected environment match `UBERWARM_ONE_SHOT_PROBE_ID`, `UBERWARM_ONE_SHOT_EXECUTION_ALLOWED=true`, protected provider Winnr token and mailbox user ID, database primary connection, exact sender and receiver IDs, and a locked `UBERWARM_ONE_SHOT_EVIDENCE_PATH` envelope with an immutable one-message batch and HMAC owner approval. It refuses to use any general `OUTBOUND_ENABLED=true` / `UBERWARM_SEND_ENABLED=true` setting. Missing or expired scope produces **zero provider submissions** before opening the primary ledger. It verifies primary/not-in-recovery and that the one-shot claim table is present, then delegates actual one-shot handling to the existing `createUberWarm2AuthorizedOneShotRuntime`, original live supplier gates, PostgreSQL atomic caps/reservation and included Winnr HTTPS send. The returned status does NOT claim Inbox placement; only a real receiving-provider observation can establish that. No automatic retries.

`src/uberwarm2-attested-one-shot-readers.mjs` supplies six independent **PINNED Ed25519 public-key** verifier roles: independent transport operator, owner risk operator, DNS authentication operator, authenticated recipient controller, receiver availability operator, and recipient suppression operator. The six public keys must be pinned by an actual trusted protected runtime, not supplied as authoritative by the untrusted manifest. The same public key reused under multiple operator labels refuses configuration. Every reader obtains the evidence file afresh, enforces exact queried identity, short 60-second observation/expiry window, and cryptographically checks the detached signature. It rejects unsigned claimed booleans and source edits. It cannot generate source attestations or owner approvals and cannot turn domain TXT presence or provider `Active` into cryptographic proof. A correct Ed25519 signature authenticates the **issuer holding the private key**, but **a key somebody just minted does not certify the claims or establish the operator's real authority**. Each signer needs separate verifiable custody and genuine underlying evidence from the appropriate original source before any positive attestation is admissible.
