## Mission

Operate UberMind continuously for approximately **USD 1/day = USD 30/month of AI cognition spend** while preserving the current moving-Crown quality contract for all important finished work.

"24/7" means the cognitive organism is always available, observing, queuing, compiling, retrieving, testing and scheduling.

It does **not** mean expensive models continuously decode tokens when there is no information-bearing work.

## Non-negotiable quality law

Important finished work must be:

1. direct current-Crown quality;
2. Crown-verified semantic delta;
3. bounded path already certified equivalent to the current Crown;
4. deterministic / reality-settled exact output;
5. otherwise queued, batched or escalated.

Budget exhaustion may reduce latency/throughput. It may not silently reduce required quality.

## Daily budget geometry

Nominal daily allowance:

```
$1.00/day
≈ $30/month
```

Default conceptual envelope:

```
$0.50  protected Crown escrow
$0.20  ultra-cheap mass cognition
$0.15  cheap-strong / diverse cognition
$0.10  stronger specialist escalation
$0.05  reserve / variance / audit

```

This is not a mandatory daily burn.

Unused budget accumulates inside the monthly ceiling.

A quiet day may spend nearly zero.

A hard day may spend more than $1 if earlier days under-spent, provided the monthly cap and protected Crown reserve remain intact.

## What $1/day can physically buy

Illustrative only, because real token composition varies.

At an 80% input / 20% output mix:

```
$0.20 MiMo Flash
blended cost ≈ $0.168/M total tokens
≈ 1.19M total model tokens/day

$0.15 DeepSeek V4.1 batch
blended cost ≈ $0.1568/M
≈ 0.96M total model tokens/day
```

So the mass layer alone can plausibly have **millions of cheap model tokens/day** before cache/reuse improvements.

For Opus:

```
$0.50/day fresh only,
80% input / 20% output
≈ 69k total tokens/day

$0.50/day fresh only,
90% input / 10% output
≈ 89k total tokens/day
```

But UberMind should avoid fresh-prefix repetition.

If most Opus input is cache-read and outputs are semantic patches rather than regenerated artifacts, the same $0.50 can cover substantially more total Opus-context traffic.

The goal is therefore not "maximize Opus tokens."

The goal is:

```
maximize important Opus-quality artifacts
per paid frontier semantic token
```

## Hourly scheduler law

Do not divide $1 mechanically into 24 equal inference slices.

Use an event-driven token bucket:

```
monthly_cap = $30
protected_crown_escrow >= $15
daily_soft_target = $1
hourly_hard_burn = dynamic
```

Each hour:

1. ingest events;
2. serve exact/cache/code hits;
3. serve certified Jev/task-compiler hits;
4. coalesce equivalent unresolved semantic atoms;
5. run cheap evidence/exploration work;
6. batch non-urgent frontier debt;
7. page Crown only when:
   - deadline requires it;
   - stakes require it;
   - accumulated shared demand justifies it;
   - novelty cannot be resolved below Crown;
8. otherwise keep the semantic debt queued.

## Quality-preserving adaptive budget policy

### GREEN — plenty of Crown reserve

Use Crown on:
- novel hard work;
- high-value teacher calls;
- certification;
- strategic meta-compiler improvements.

### YELLOW — Crown reserve tightening

Increase:
- batch delay;
- shared semantic debt coalescing;
- cheap evidence gathering;
- output surgery;
- cache locality.

Do not reduce required final quality.

### RED — protected reserve boundary reached

Do not let low-priority work consume Crown escrow.

```
non-urgent novelty -> queue
urgent high-stakes -> Crown
ordinary certified work -> continue
cheap exploratory work -> only if expected to reduce future Crown demand
```

### BLACK — monthly budget exhausted

```
exact / already-certified work -> continue if inference-free
new paid cognition -> stop
important unresolved work -> queue
```

No silent quality downgrade.

## Honest feasibility boundary

A $1/day budget cannot guarantee unlimited fresh arbitrary frontier cognition.

If every incoming task is truly novel, high-stakes and requires direct Opus-level semantic work, throughput must fall and tasks must queue.

The architecture becomes powerful when:
- tasks recur;
- evidence overlaps;
- decisions share subproblems;
- outputs can be patched;
- correctness can be verified cheaply;
- semantic structures can be compiled;
- accumulated cognition survives future tasks.

The system's job is to turn more of reality into those conditions over time.
